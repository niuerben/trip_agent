# 立项方案：Talk 上下文窗口压缩 + 用户偏好向量库（跨会话时间加权召回）

> 本文一次立项覆盖两个配套能力：**对话上下文 16k 字符窗口 + 超限自动滚动摘要**，以及**用户偏好写入 Chroma 向量库并跨会话语义召回**。两者同属"对话记忆"主题，一次立项、一个 spec。
>
> **本次不做**：tokenizer 精确计数、摘要落库（Postgres）、提前压缩余量、偏好管理界面、跨用户偏好共享、Postgres 偏好表结构变更、前端行为变更（仅同步可选类型字段）。

## Context（为什么改）

### 上下文无界增长

- `talk.py` 的 `_load_history`（`talk.py:31`）把 `chat_messages` 表里该会话**全部**记录升序取出，无任何截断。
- `plan_context` 是完整 `TripPlan` 的 JSON dump（前端/`trip.py:74`），一次 2 日行程即数千字符，多日行程更快。
- `build_talk_prompt`（`plan_agent.py:133`）把城市、行程摘要、偏好、全量历史拼进 `TALK_AGENT_PROMPT`；`_build_suggestion_prompt` 再拼一次同样的全量历史。多轮对话后提示词必然超出模型上下文预算，表现为长会话下对话质量劣化乃至请求失败。

### 偏好是会话级 KV，没有语义检索能力

- 偏好只存 Postgres `conversation_preferences`（一行/会话，`talk.py:180` 写入），按 `conversation_id` 精确读取。用户在历史会话里确认过的偏好（"喜欢大学校园""不吃辣"）无法在**新会话**中被利用。
- Chroma 目前只有 POI 库（`poi_vector_store.py`，collection `amap_pois`），与用户偏好无关。

### 最终决策（已与需求方逐项确认）

- **token 按字符数直算**：中文场景 1 字 ≈ 1 token，不做 tokenizer 引入，**不做提前压缩余量**——只有提示词总长实际超过 16384 字符才触发压缩。
- **偏好召回跨会话（同用户）**：召回范围是该用户全部历史会话，不是仅当前会话。
- **过期偏好用时间加权处理**：评分 `score = 语义相关度 × 0.5^(天数/半衰期)`，半衰期默认 90 天；不做"只取最近一条"的硬截断。
- **摘要只做进程内存缓存，不落库**：重启后丢失缓存仅多一次 LLM 摘要调用，不影响正确性；不为此新建表。

## 方案

### 1) 上下文压缩：`backend/app/services/context_compactor.py`（新建）

**窗口与预算**：`config.py` 新增 `talk_max_context_tokens=16384`、`talk_context_keep_recent_messages=8`。

**触发条件**：`build_talk_prompt` 用空 history 先渲染一次模板得到基础长度，`history_budget = 16384 - 基础长度 - 头部上下文长度`；聊天历史总长 ≤ budget 时**原样使用，不调 LLM**。

**压缩策略**（只压聊天历史，头部事实上下文不动）：

- 保留最近 8 条消息原文；
- 更早消息做**滚动摘要**：`新摘要 = LLM(已有摘要 + 新增旧消息)`，提示词要求只保留目的地、日期、同行人、已确认偏好/禁忌、预算、已执行修改、未落实意向，输出 ≤300 字；
- 摘要按 `conversation_id` 缓存在进程内 `OrderedDict`（容量 256，LRU 淘汰），缓存记录"已摘要条数"，下次只摘要增量片段。

**降级路径**（逐条）：

| 场景 | 行为 |
| --- | --- |
| LLM 摘要调用失败 | 丢弃旧消息，只保留最近原文（从最旧开始截），永不突破窗口 |
| 摘要本身超预算 | 截断摘要文本 |
| 摘要 + 最近原文仍超限 | 继续丢最旧的原文，**永远保留最新一条** |
| 无 conversation_id（未落库会话） | 不缓存，每轮重摘要 |
| 头部上下文已占满窗口（budget ≤ 0） | 只保留最新一条消息 |

**接入点**：`build_talk_prompt(request, compactor=None)`（可选参数，向后兼容，两个既有单测直接导入该函数）与 `PlanAgent._build_suggestion_prompt`（共用同一窗口预算）。`PlanAgent.__init__` 创建 `self.compactor = ContextCompactor(llm=self.llm)`；`compactor` 同时有**类级默认 None**，使绕过 `__init__` 的测试构造自然退回不压缩行为。

### 2) 偏好向量库：`backend/app/services/preference_vector_store.py`（新建）

**存储**：与 POI 库共用 Chroma 持久化目录（`chroma_persist_directory`），独立 collection `preference_collection_name="user_preferences"`，cosine 空间。

**主键设计**：文档 ID = `sha1(user_id|conversation_id)` —— 同一会话偏好更新**覆盖**旧值不堆积，不同会话各自保留。metadata：`user_id / conversation_id / city(归一化) / updated_epoch(float) / updated_at(北京时间 ISO)`。

**召回算法**：

```
score = (1 - distance) × 0.5 ^ (age_days / preference_recency_half_life_days)
```

- `where={"user_id": user_id}` 硬过滤，跨用户零泄漏；
- 超过 `preference_vector_distance_threshold=0.8` 的候选直接丢弃（阈值比 POI 的 0.55 宽松，偏好文本短且语义分散）；
- 先取 `min(库内总数, max(top_k×5, 50))` 条候选，加权排序后取 `preference_vector_top_k=5`。

**配置**（`config.py`）：`preference_collection_name` / `preference_vector_top_k=5` / `preference_vector_distance_threshold=0.8` / `preference_recency_half_life_days=90.0`。

**降级路径**：Chroma 不可用（未装依赖/打开失败）时 `get_preference_vector_store()` 返回 None，所有调用方按"无召回"处理，主链路不受影响——与 `get_poi_vector_store()` 既有模式一致。

### 3) Schema 与前端类型：最小改动

- `schemas.py` 的 `TalkRequest` 新增可选字段 `recalled_preferences: Optional[List[str]]`；Postgres 表结构零改动。
- `frontend/src/types/index.ts` 的 `TalkRequest` 同步新增可选 `recalled_preferences?: string[]`；前端不发该字段（由后端注入），行为不变。

### 4) 写入链路：`talk.py`

偏好落 Postgres 成功后，同步 upsert 到向量库（`asyncio.to_thread`，不阻塞事件循环）：

- 条件：`conversation_id` 存在且本轮提炼出 `preference.prompt`；
- 独立于 Postgres 的 try/except，失败仅打日志，不影响对话返回。

### 5) 召回链路：`talk.py` 与 `trip.py`

**`/talk` 对话前**：召回查询词 = `城市 + 用户本轮输入`；排除当前会话自己的行（当前会话以 Postgres 权威版本为准，避免双源不一致）；结果经 `TalkRequest.recalled_preferences` 注入提示词，`/talk/suggestions` 恢复建议时同样注入（查询词 = 城市）。

**`/trip/plan` 规划前**：召回查询词 = `城市 + 当前偏好文本`，结果**并入本次规划使用的偏好文本**——只影响本次规划，不回写 `conversation_preferences`。

**提示词契约**：`build_talk_prompt` 与建议提示词新增 `[相关历史偏好]` 段，并固定声明语义："来自用户历史会话的语义召回，仅供参考，与当前行程冲突时以当前行程和用户本轮表述为准"——防止历史偏好压过本轮显式诉求。

## 风险与已接受的代价

| 风险 | 处置 |
| --- | --- |
| 字符数 ≠ 精确 token，英文混排时偏差更大 | 已接受：用户明确"按字数算 token 就行了"；16k 窗口对偏差有足够冗余 |
| 首次触发压缩的那一轮多一次 LLM 往返 | 已接受：仅超限时发生，且增量缓存后每轮只摘要新增片段 |
| 进程重启丢失摘要缓存 | 已接受：重摘要只多一次调用，不影响正确性 |
| 召回的历史偏好与本轮诉求冲突 | 提示词固定声明"以当前行程和本轮表述为准"；时间加权使近期偏好天然占优 |
| uvicorn 多 worker 部署下内存缓存不共享 | 仅浪费（各自重摘要），不产生错误；当前单进程部署无影响 |

## 验证

```powershell
python -m unittest test.unit.test_context_compactor -v        # 压缩：预算判定/滚动摘要/增量缓存/失败降级/必留最新
python -m unittest test.unit.test_preference_vector_store -v  # 偏好：同会话覆盖/用户隔离/时间加权/距离过滤
python -m unittest discover -s test/unit -p "test_*.py" -v    # 默认门禁
```

两个新测试文件均进默认门禁：`test_context_compactor.py` 用注入的 fake summarizer，无 LLM 依赖；`test_preference_vector_store.py` 用临时目录 Chroma（模式同 `test_poi_vector_store.py`）。真实 LLM/高德链路不受本次改动影响，无需新增真实服务验收。
