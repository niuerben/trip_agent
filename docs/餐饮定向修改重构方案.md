# 重构方案：餐饮定向修改链路（不做子分类 · 统一按餐饮检索）

> 本文是 [`意图识别-servicece层重构.md`](意图识别-servicece层重构.md) 宏观方向下的一次**聚焦落地**：只处理"修改餐馆"这条定向修改（`change_set`）主链，范围经与需求方逐项确认后收窄——**不做任何餐饮子分类、只用 keywords、本次不动 `Meal.type`、不改 ReAct 兜底**。宏观文档中的 IntentRecognizer / ChangeSetService / ConstraintEngine 等长期演进不在本次范围内。

## Context（为什么改）

用户要求"修改餐馆"（如"第二天午餐换成火锅""别吃面了换一家"）经常失败。根因是**餐饮意图在整条链路里没有结构化落脚点**，只能被塞进自由文本 `semantic`，service 再靠脆弱字符匹配去兜：

- **schema 太松**：`ChangeTarget`（`schemas.py:22-25`）只有 `name`/`semantic`，无法表达"吃什么/在哪附近/餐段/预算"。
- **prompt 教了非普遍模式**：`TALK_AGENT_PROMPT`（`talk_agent.py:38`）的 `replace_meal` 示例直接让模型输出 `"…非面类餐厅"`，把"非面"这种无普遍价值的写法固化进意图层。
- **service 只会排除面条**：`_resolve_replacement_meal_poi`（`trip_planning_service.py:1456-1502`）剥离 `非面/早餐` 字样、纯关键词搜 `f"{area} 餐厅"`、再套硬编码 noodle 黑名单 `("面馆","面店","拉面",…)` + 早餐关键词加权。正向诉求（火锅）被忽略；候选被黑名单清空时返回 `None` → `poi_not_found` → 回退 ReAct → 超时/失败，即当前现象。
- **高德 `types` 从未使用**：两个高德调用都是纯 `keywords`，从不传 `types`。

**最终决策（已与用户逐项确认）**：
- **不划分、不自造任何餐饮分类**（无 CuisineCategory 枚举、无 typecode 子分类）。所有餐饮一视同仁：统一用 `types=050000`（餐饮服务根类）兜底检索，"吃什么"全部写进 `keywords`。
- **"排除某类"不做结构化**：直接删除 noodle 黑名单，不引入 `exclude`。
- 本次**不动** `Meal.type`（保持 `str`），不改前端类型、不迁移历史数据。
- **聚焦定向修改（change_set）主链**，不改 ReAct 兜底 / 证据预取路径。

**目标**：schema 严格（把混在 `semantic` 里的"菜品+地点+餐段+预算"拆成明确字段）、意图识别只做"提炼诉求成 keywords/结构化字段"而不做人为分类、service 用统一 `types=050000`+`keywords` 检索并**彻底删除所有针对特定子类的字符匹配**。

## 方案（三层 + 一个常量）

### 1) Schema 收紧 `backend/app/models/schemas.py`
新增（**无任何分类字段**）：
```python
class DiningTarget(BaseModel):
    """餐饮替换目标：统一按餐饮检索，诉求写进 keywords，不做子分类。"""
    keywords: Optional[str] = Field(default=None, description="想吃什么: 火锅 / 日本料理 / 清真 / 店名等")
    near: Optional[str] = Field(default=None, description="地点锚: 如 钱江世纪公园附近")
    max_cost_per_person: Optional[int] = Field(default=None, ge=0, description="人均预算上限(元)")
    meal_type: Optional[Literal["breakfast","lunch","dinner","snack"]] = Field(default=None, description="餐段提示，用于检索兜底与打分")
```
`ChangeTarget` 增加字段（保留 `name`/`semantic` 给景点，向后兼容）：
```python
class ChangeTarget(BaseModel):
    name: Optional[str] = None
    semantic: Optional[str] = None
    dining: Optional[DiningTarget] = None    # replace_meal 专用
```
> 严格性体现在：把原来 `semantic` 字符串里混杂的地点/预算/餐段/菜品拆成类型明确的字段；`meal_type` 用 `Literal` 就地约束（不新建全局 `MealType` 枚举，不动 `Meal.type`）。

### 2) 意图识别 `backend/app/agents/talk_agent.py`
- 改写 `TALK_AGENT_PROMPT`（`talk_agent.py:33-40`）里 `replace_meal` 契约：**删除 `"…非面类餐厅"`**，改为输出 `target.dining`，把用户话语提炼为结构化字段——不做任何分类：
  - "第二天午餐换成火锅" → `{"selector":{"day_index":1,"name":"<旧午餐>"},"target":{"dining":{"keywords":"火锅","meal_type":"lunch"}}}`
  - "换家日料" → `{"dining":{"keywords":"日本料理"}}`
  - "钱江世纪公园附近找家早餐店" → `{"dining":{"near":"钱江世纪公园","meal_type":"breakfast"}}`
  - **否定诉求（"别吃面"）**：引导 LLM 转成正向——若用户点明想吃别的就填 `keywords`；否则 `keywords` 留空（=换一家同餐段餐厅）。**不再产生任何 `非面` 字样**。
- 不改 `_has_explicit_replan_intent` / `_is_negative_replan` / `_date_confirmation` 等 chat↔replan 门控（另一职责，避免回归）。

### 3) Service：统一 `types=050000` + `keywords`，删除所有子类字符匹配
- **`amap_photo_service.py`**：`search_pois`（`:107`）/ `_fetch_pois`（`:44-78`）增加可选参数 `types: Optional[str] = None`，非空时透传高德 `types`（与 `keywords` 并存）。
- **重写 `_resolve_replacement_meal_poi`（`trip_planning_service.py:1456-1502`）**，签名改为接收 `DiningTarget`：
  1. `keywords = " ".join(filter(None, [dining.near, dining.keywords])).strip()`；为空时兜底 `meal_type` 中文餐段词或 `f"{city} 餐厅"`。
  2. `search_pois(keywords, city=amap_city, offset=20, types=DINING_ROOT_TYPECODE)`（统一 `050000`）。
  3. adcode 硬过滤（沿用 `:1485-1486`）+ `classify_poi_group(poi)=="meal"`。
  4. **删除**：noodle 黑名单 `excluded`（`:1479`）、`非面/早餐` 字符串剥离（`:1465`）、早餐关键词加权（`:1494`）。
  5. 打分：`near` 命中加权 + `max_cost_per_person` 过滤（结构化）；空结果时**降级重搜**（仅 `types`/仅 city 关键词），避免 `keywords` 过窄导致高德交集为空。
- **`_LegacyAttractionResolver.resolve_attraction`（`trip_planning_service.py:1287-1294`）** 的 `replace_meal` 分支：把 `target.dining` 传入新 resolver；`dining` 为空时用 `semantic`/`name` 兜底构造 `DiningTarget(keywords=…)`（**不再套黑名单**），保证旧 change_set / 历史前端仍可执行。
- **`classify_poi_group`（`poi_vector_store.py:21-51`）** 改 **typecode 优先**：先按 `typecode` 前缀判三大组（`05`→meal / `10`→hotel / `11,14,15,16,18`→attraction），无 typecode 再用现有关键词回退；accessory（公交站/停车场等）排除保留。减少对字符匹配的依赖（三大组归类保留，**不涉及餐饮子分类**）。
- 常量 `DINING_ROOT_TYPECODE = "050000"` 就近定义（如 `poi_vector_store.py` 或 `config.py`），**不新建 taxonomy 模块**。

> `types=050000` 依据：`docs/高德POI分类与编码（中英文）_V1.06_20230208.xlsx`（高德官方分类表），餐饮服务根类为 `050000`，高德"大类含子类"，传根类可召回全部餐饮。

## 分阶段实施（低耦合优先）
1. **schema**（`DiningTarget` + `ChangeTarget.dining`）——独立、向后兼容。
2. **`classify_poi_group` 改 typecode 优先** + `DINING_ROOT_TYPECODE` 常量——独立，可先回归。
3. **Amap `types` 透传**——独立，默认 `None` 不影响现有调用。
4. **重写 `_resolve_replacement_meal_poi` + resolver 传 `dining`**——依赖 1/3，删所有子类字符匹配。
5. **改写 prompt 契约**——依赖 1，最后接通端到端。

## 向后兼容与风险
- **旧 `target`（仅 semantic）**：resolver 兜底构造 `DiningTarget(keywords=semantic)`，走统一 `050000`，能替换、不再误排面馆。
- **历史 `current_plan`**：`Meal.type` 保持 `str`，无迁移。
- **`types` 与 `keywords` 同传取交集**：`keywords` 过窄可能返回空 → resolver 内置降级重搜（仅 types / 仅 city）。
- **`types=050000` 兜底**：高德"大类含子类"，餐饮服务根类返回全部餐饮，安全。

## 验证（端到端）
1. `cd backend && python run.py`，`http://localhost:8000/docs`。
2. **意图层**：POST `/api/talk`，message="把第二天午餐换成火锅"，断言 `change_set.operations[0].target.dining == {"keywords":"火锅","meal_type":"lunch",...}`，且**无 `非面` 字样**。
3. **执行层**：把上一步 `change_set` + 一份 `current_plan` 发 POST `/api/trip/plan`，断言第二天对应餐被替换为火锅店（`poi_id`/`location`/`address` 齐全）。
4. **删除验证**：message="别吃面了换一家"，断言产出的 `dining` 不含 `非面`，且替换成功（不因黑名单清空候选而失败）。
5. **回归**：普通"换一家餐厅"（`dining` 为空/仅 semantic）仍能成功替换；`types=050000` 兜底可用。
6. e2e：`python test/test_trip_planner.py`（覆盖规划主流程）；餐饮替换对话可另写最小脚本直打 `/api/trip/plan`。
