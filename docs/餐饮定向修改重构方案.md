# 重构方案：餐饮定向修改链路（不新增 schema · 不做子分类 · 统一按餐饮检索）

> 本文是 [`意图识别-servicece层重构.md`](意图识别-servicece层重构.md) 宏观方向下的一次**聚焦落地**：只处理"修改餐馆"这条定向修改（`change_set`）主链，范围经与需求方逐项确认后收窄——**不新增 schema、不做任何餐饮子分类、只用已有字段承载 keywords、本次不动 `Meal.type`、不改 ReAct 兜底**。宏观文档中的 IntentRecognizer / ChangeSetService / ConstraintEngine 等长期演进不在本次范围内。

## Context（为什么改）

用户要求"修改餐馆"（如"第二天午餐换成火锅""别吃面了换一家"）经常失败。根因是**餐饮意图在整条链路里没有稳定约定**，只能被塞进自由文本，再由 service 靠脆弱字符匹配去兜：

- **餐饮目标没有统一语义约定**：`ChangeTarget`（`schemas.py:22-25`）已有 `name`/`semantic`，但 `replace_meal` 没有明确约定使用哪个字段承载检索关键词，导致地点、菜品诉求被拼成特殊化文本。
- **prompt 教了非普遍模式**：`TALK_AGENT_PROMPT`（`talk_agent.py:38`）的 `replace_meal` 示例直接让模型输出 `"…非面类餐厅"`，把"非面"这种无普遍价值的写法固化进意图层。
- **service 只会排除面条**：`_replace_meal`（`trip_planning_service.py:1456-1502`）剥离 `非面/早餐` 字样、纯关键词搜 `f"{area} 餐厅"`、再套硬编码 noodle 黑名单 `("面馆","面店","拉面",…)` + 早餐关键词加权。正向诉求（火锅）被忽略；候选被黑名单清空时返回 `None` → `poi_not_found` → 回退 ReAct → 超时/失败，即当前现象。
- **高德 `types` 从未使用**：当前高德关键词搜索调用是纯 `keywords`，没有透传 `types`。

**最终决策（已与用户逐项确认）**：

- **不新增 schema**：复用现有 `ChangeTarget.semantic` 作为餐饮检索 `keywords`；若模型只填写 `target.name`，service 将其作为兼容性兜底。`schemas.py` 本次零改动。
- **不划分、不自造任何餐饮分类**（无 CuisineCategory 枚举、无 typecode 子分类）。所有餐饮一视同仁：统一用 `types=050000`（餐饮服务根类）兜底检索，"吃什么"全部写进已有 `semantic`。
- **"排除某类"不做结构化**：直接删除 noodle 黑名单，不引入 `exclude`。
- 本次**不动** `Meal.type`（保持 `str`），不改前端类型、不迁移历史数据。
- **聚焦定向修改（change_set）主链**，不改 ReAct 兜底 / 证据预取路径。

**目标**：不扩张 schema；意图识别只把用户话语提炼成已有 `target.semantic` 检索关键词，不做人为分类；service 用统一 `types=050000` + keywords 检索并**彻底删除所有针对特定子类的字符匹配**。

## 方案（三层 + 一个常量）

### 1) Schema：本次不改 `backend/app/models/schemas.py`

不新增 `DiningTarget`，不新增餐饮枚举，也不扩展 `ChangeTarget`。`replace_meal` 复用已有字段：

- `target.semantic`：餐饮检索关键词（菜品、餐厅名、地点等自然语言诉求均可放入）。
- `target.name`：当旧调用方或模型没有填写 `semantic` 时，作为兼容性兜底关键词。
- `selector.name` / `selector.day_index`：继续负责定位原有餐饮节点。

这样既不继续膨胀 schema，也不把餐段、菜系、排除项伪装成新的分类字段。`Meal.type` 保持现状，不做修改。

### 2) 意图识别 `backend/app/agents/talk_agent.py`

改写 `TALK_AGENT_PROMPT`（`talk_agent.py:33-40`）里 `replace_meal` 契约：删除 `"…非面类餐厅"` 这种特殊化示例，改为把用户明确的正向诉求写入已有的 `target.semantic`。

示例：

- "第二天午餐换成火锅" → `{"selector":{"day_index":1,"name":"<旧午餐>"},"target":{"semantic":"火锅"}}`
- "换家日料" → `{"target":{"semantic":"日本料理"}}`
- "钱江世纪公园附近找家早餐店" → `{"target":{"semantic":"钱江世纪公园 早餐店"}}`
- "别吃面，换成火锅" → `{"target":{"semantic":"火锅"}}`
- "别吃面了换一家" → `{"target":{"semantic":""}}` 或省略 `target.semantic`，表示在原餐段换一家通用餐厅；不得生成 `非面`、`不含面` 等人为排除关键词。

不改 `_has_explicit_replan_intent` / `_is_negative_replan` / `_date_confirmation` 等 chat ↔ replan 门控。

### 3) Service：统一检索并清理特殊匹配

#### Amap types 透传

`amap_photo_service.py` 的 `search_pois` / `_fetch_pois` 增加可选 `types` 参数，默认 `None`，不影响其他调用。非空时透传到高德 `/v3/place/text` 的 `types` 参数，与 `keywords` 并存。

#### `TripPlanningService` 命名与逻辑

餐饮定向替换统一使用 `_replace_meal`。这个名字与已有 `_replace_attraction` 保持一致：**一个动词 + 一个名词，语言直接说明行为**。不引入 `_resolve_replacement_meal_poi` 这类绕行命名。

`_replace_meal` 的职责：按餐饮目标检索并选出替换 POI。

执行逻辑：

1. 从 `target.semantic` 读取 keywords；若为空，再回退 `target.name`；仍为空时使用 `f"{city} 餐厅"` 作为通用兜底。
2. 调用 `search_pois(keywords, city=amap_city, offset=20, types=DINING_ROOT_TYPECODE)`，统一使用 `types=050000` 餐饮服务根类。
3. 保留 `target_adcode` 硬过滤、有效坐标校验和 `classify_poi_group(poi) == "meal"`。
4. 删除 noodle 黑名单、`非面/早餐` 字符串剥离和早餐词加权；不引入 `exclude` 或餐饮子分类。
5. 首次查询无合格结果时执行有限降级：用城市通用餐厅关键词继续按 `types=050000` 查询；仍无结果再返回 `None`，交由现有失败处理。

`_LegacyAttractionResolver.resolve_attraction` 的 `replace_meal` 分支继续调用 `_replace_meal`；读取目标时优先用 `target.semantic`，再回退 `target.name`。旧 `change_set` 不需要迁移。

### 4) POI 分组：typecode 优先，但组集不变

`classify_poi_group` 可改为 typecode 优先，但必须保持对外分组集合不变：

```python
POI_GROUPS = ("attraction", "hotel", "meal")
```

归类边界：

- `05` → `meal`
- `10` → `hotel`
- `11` / `14` / `15` / `16` / `18` → `attraction`
- 无可识别 typecode 时使用现有关键词回退。
- 公交站、地铁站、停车场、出入口等 accessory 排除规则保留，仍返回 `None`。
- 不增加 `dining`、`restaurant`、`food`、`transport` 等新组。

兼容不变量：已有三大组仍只可能返回 `attraction` / `hotel` / `meal`；不能因为 typecode 优先而让附属 POI 重新进入候选；不能把餐饮再拆成任何子组。

### 5) 常量

就近定义：

```python
DINING_ROOT_TYPECODE = "050000"
```

建议放在 `poi_vector_store.py` 或餐饮替换调用最集中的 service 旁边，避免新建 taxonomy 模块。

> `types=050000` 依据：`docs/高德POI分类与编码（中英文）_V1.06_20230208.xlsx`（高德官方分类表），餐饮服务根类为 `050000`，高德"大类含子类"，传根类可召回全部餐饮。

**复用的现有逻辑**：adcode 硬过滤；`_parse_poi_location`；`ChangeSetExecutor._meal`（保留原 `Meal.type`）；`_normalize_city_for_amap`。**不新增** `poi_taxonomy.py`。

## 分阶段实施（低耦合优先）

1. **prompt**：改 `replace_meal` 示例，删除 `非面`，明确餐饮目标写入 `target.semantic`。
2. **POI 分组**：`classify_poi_group` 改 typecode 优先，保证返回组集仍为 `attraction` / `hotel` / `meal` / `None`。
3. **Amap `types` 透传**：默认 `None`，现有调用不变。
4. **`TripPlanningService._replace_meal`**：统一命名，重写餐饮替换检索；使用 `types=050000`；删除特殊化字符串匹配。
5. **回归验证**：覆盖意图层、service 层、POI 分组和现有规划主流程。

## 向后兼容与风险

- **旧 `target`（仅 semantic）**：继续可用；`semantic` 作为 keywords 走统一 `050000`。
- **旧 `target.name`**：当 `semantic` 为空时作为兜底 keywords。
- **历史 `current_plan`**：`Meal.type` 保持 `str`，无迁移。
- **`types` 与 `keywords` 同传取交集**：keywords 过窄可能返回空 → `_replace_meal` 内置一次城市通用餐厅降级查询。
- **POI 分组**：只改变判定顺序，不改变对外组集；typecode 不可识别时仍保留关键词回退。

## 验收标准

### A. Schema 边界

- `backend/app/models/schemas.py` 没有新增 `DiningTarget`、`CuisineCategory`、`MealType` 或其他餐饮专用模型/枚举。
- `ChangeTarget` 字段保持 `name` / `semantic` 现状，不新增 `dining` / `near` / `exclude` / `max_cost_per_person` 等字段。
- `Meal.type` 仍为 `str`，前端类型不需要同步修改。

### B. 意图识别

- `/api/talk` 输入 `把第二天午餐换成火锅` 时，`change_set.operations[0].operation == "replace_meal"`，目标关键词落在 `target.semantic == "火锅"` 或等价正向关键词。
- `/api/talk` 输入 `别吃面，换成火锅` 时，输出不得包含 `非面` / `不含面` / `not noodle` 等排除型关键词，`target.semantic` 应表达正向诉求 `火锅`。
- `/api/talk` 输入 `别吃面了换一家` 时，可以不生成具体 keywords，但不能生成 `非面类餐厅` 这类伪分类/排除词。

### C. Service 检索链路

- `TripPlanningService` 中餐饮替换方法命名为 `_replace_meal`，与 `_replace_attraction` 风格一致；不得新增 `_resolve_replacement_meal_poi` 这类绕行命名。
- `_replace_meal` 使用 `target.semantic` / `target.name` 作为 keywords，并调用高德搜索时传 `types=DINING_ROOT_TYPECODE`。
- `_replace_meal` 中不存在 noodle 黑名单、`非面` 字符串剥离、早餐关键词加权等特殊化逻辑。
- 当 keywords 搜索无合格餐饮候选时，至少有一次基于城市通用餐厅关键词 + `types=050000` 的降级搜索。
- 替换成功的餐饮 POI 具备 `name`、`address`、`location`、`poi_id`，并继续由 `ChangeSetExecutor._meal` 保留原餐段 `Meal.type`。

### D. POI 分组

- `POI_GROUPS` 仍等于 `("attraction", "hotel", "meal")`，没有新增或改名。
- `classify_poi_group` 的返回集合只允许为 `"attraction"` / `"hotel"` / `"meal"` / `None`。
- typecode 优先规则生效：`05xxxx` 为 meal、`10xxxx` 为 hotel、`11/14/15/16/18xxxx` 为 attraction。
- 无 typecode 或旧 Chroma 元数据缺失 typecode 时，现有关键词回退仍可用。
- 公交站、地铁站、停车场、出入口等 accessory POI 仍返回 `None`，不能进入三大候选组。

### E. 端到端行为

- `change_set` + `current_plan` 发 POST `/api/trip/plan`，把第二天午餐换成火锅，应成功替换为餐饮服务 POI，且不触发 `poi_not_found`。
- 普通 `换一家餐厅` 在没有具体 keywords 时仍可用城市通用餐厅兜底成功替换。
- 景点替换、新增景点、日期修改等既有 `change_set` 操作不回归。
- `python -m compileall backend/app` 通过；现有 `test/test_trip_planner.py` 在前后端启动条件下仍可跑通主流程。
