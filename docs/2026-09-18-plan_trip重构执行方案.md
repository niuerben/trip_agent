# `plan_trip()` 重构执行方案

> 本文是 `TripPlanningService.plan_trip()` 的重构执行规划，基于 2026-09-18 对
> `backend/app/services/trip_planning_service.py:138-409` 的逐行核对。
>
> 本文与 `docs/2026-09-11-service层重构-基于现状.md`（下称"0911 方案"）对齐：
> 骨架沿用其 CP0-CP7 渐进路径，合并外部评审中验证成立的改进点，激进的目录
> 重构推迟到测试覆盖之后。
>
> 本文只做规划，不修改代码。

## 1. 背景

外部评审对 `plan_trip()` 提出 14 条批评，核心诊断是：

1. 它已经不是普通 Service，而是一个隐式状态机；
2. 业务编排和基础设施调用混在一起；
3. Create / Replan / Deterministic / ReAct / Fallback 全塞进一个函数。

这三条与 0911 方案 §3 的判定一致。本文先逐条核对批评是否成立，再给出
可执行的阶段划分。

## 2. 批评逐条核对结果

对照 `trip_planning_service.py` 当前代码（行号以 2026-09-18 工作区为准）：

| # | 批评点 | 结论 | 依据 |
| --- | --- | --- | --- |
| 1 | `plan_trip()` 职责过载 | ✅ 成立 | 约 270 行，17 类职责；与 0911 方案 §3.1 一致 |
| 2 | 控制流已形成嵌套状态机 | ✅ 成立 | 确定性排程的 refresh-重排-ReAct 回退嵌套在 `:274-329`，无显式状态表达 |
| 3 | fallback 策略隐式分散 | ✅ 成立 | Service 内多处 fallback，且 API 层 `trip.py` 还有一处，决策点分散 |
| 4 | 规划策略与基础设施耦合 | ✅ 成立 | 行政区解析 `:157-167`、天气 `:347-352` 直接内联在规划流程里 |
| 5 | `ThreadPoolExecutor` 泄漏到业务层 | ⚠️ 部分成立 | 后台线程放行是**故意设计**——`:179-181` 注释明确"超时后让向量查询自然结束为后续请求热身"。批评者未识别该意图；但并发控制写在业务方法内仍然成立 |
| 6 | `except Exception` 语义不统一 | ⚠️ 部分成立 | `TargetedReplanUnsatisfiable` 已是刻意的业务分支（`:400-403` 有注释说明不打堆栈）；但行政区/天气/Agent 失败确实都落在 `except Exception` |
| 7 | `print()` 承担日志职责 | ✅ 成立 | 全文件使用 print，无 logging |
| 8 | `trip_plan` 生命周期复杂 | ✅ 成立 | `:273` 置 None，4 个来源赋值，5 个阶段继续修改 |
| 9 | `TripPlan` 被大量原地修改 | ✅ 成立 | `:355` `trip_plan.weather_info = ...` 等 |
| 10 | `TripRequest` 塞了太多规划状态 | ✅ 成立 | 同时承载 `current_plan/change_set/change_request` |
| 11 | `change_set` 分支应独立为 use case | ✅ 成立 | `:216-248` 是独立用例"Modify Existing Trip" |
| 12 | 双 Planner 混在同一方法 | ✅ 成立 | `:274`（确定性）与 `:330`（ReAct）以 if/None 串联 |
| 13 | 策略数字散落 | ❌ 基本不成立 | `timeout=3` 实际已是 `getattr(settings, "planner_vector_retrieval_timeout_seconds", 3)`（`:198-200`）；仅 `max_workers=1` 为硬编码 |
| 14 | `settings` 在方法中间获取 | ⚠️ 夸大 | `get_settings()` 在 `:153` 方法体开头；但构造函数依赖注入确实缺失（`__init__` 仅存 `llm`，`:121-136`） |

**总评：14 条中 10 条成立、3 条部分成立或夸大、1 条不成立。核心诊断成立。**

## 4. 落地阶段

### CP0：行为基线 + 特征测试（最优先）

纯增加测试，零行为风险。引入 pytest（项目当前无单元测试框架，仅
Playwright 端到端脚本），为 `plan_trip()` 锁死 6 条关键路径：

| # | 锁定行为 | 当前位置 |
| --- | --- | --- |
| 1 | 定向修改成功直接返回，不触发全量规划 | `:216-235` |
| 2 | 定向修改校验/执行失败 → 抛 `TargetedReplanUnsatisfiable`，**不**降级全量重排 | `:236-248`（刻意设计） |
| 3 | 确定性排程 `ROUTE_LEG_TOO_LONG` → refresh 补证据重排 → 仍失败转 ReAct | `:283-329` |
| 4 | Chroma 超时 → 主线程走高德预取，后台向量查询放行热身 | `:179-205` |
| 5 | 定向修改/预加载证据模式跳过图片补齐，转前端异步加载 | `:372-377`（CLAUDE.md 明文约定） |
| 6 | ReAct 结束但无 Validator 通过的计划 → `RuntimeError`，禁止占位数据伪装 | `:337-338` |

测试策略：ReAct 路径用 fake LLM；确定性路径不依赖模型可直接跑。

### CP1：固定 `plan_trip()` 的阶段边界

纯搬编排代码，不搬算法。切成 7 个私有方法：

```text
_prepare_planning_scope      ← :152-178  行政区/半径/adcode
_retrieve_initial_pois       ← :179-205  Chroma 召回 + 线程/超时
_try_targeted_change_set     ← :206-248  定向修改
_prepare_planning_session    ← :250-272  session 构造 + 证据预取
_try_deterministic_plan      ← :274-329  确定性排程（含 refresh 重试）
_run_react_plan              ← :330-338  ReAct 兜底
_finalize_plan               ← :341-398  时间线/排序/天气/补齐/终验
```

约束：保留现有 print 与异常行为，CP0 测试必须全绿。

### CP2：规划上下文准备隔离

行政区解析结果收敛为一个返回值
（`city / amap_city / city_center / radius_km / target_adcode`）。
不改变 `_DISTRICT_SCOPES` 映射、区县判定和 adcode 过滤逻辑。

### CP3：初始 POI 召回边界

`_retrieve_cached_pois` 输入输出签名固定
（`TripRequest, Preference, adcode, amap_city -> list[dict]`）。
线程池、超时、**热身语义**一起下沉到召回边界内，调用侧只剩一次调用。
热身行为保留并转为显式参数或注释（回应批评 #5，但不删除现有意图）。

### CP4：双 Planner 统一结果约定

```text
确定性 Planner: try_plan(session) -> TripPlan | None（附失败原因）
ReAct Planner:  plan(session)     -> TripPlan | None
```

回退方向保持现状：确定性失败 → ReAct，不允许反向。
`PlanningToolset` 不承担 Service 级 fallback。

### CP5：定向修改独立成用例

```python
def plan_trip(...):
    if self._is_targeted_replan(request):
        return self._replan_trip(...)
    ...
```

`_LegacyAttractionResolver` 移出 `TripPlanningService` 成可独立测试的类
（0911 方案 §3.3 遗留问题）。**实施前先与
`2026-09-14-餐饮定向修改重构方案.md` 对账，避免两方案冲突。**

### CP6：后处理管线固定顺序

`_finalize_plan` 内顺序固定：

```text
时间线补齐 → 近邻排序 → 天气补齐 → 按模式决定图片/餐饮补齐 → 最终 Validator
```

跳过图片补齐的条件表达式必须保持原语义，`:366-371` 的设计注释随代码搬迁。

### CP7：失败分类 + 日志（最后做）

1. `print` 全部换成 `logging`，结构化字段包含
   `city / travel_days / planning_mode / poi_source / fallback_reason`。
2. 异常分类**先文档化后代码化**：先维护 0911 方案 CP7 的失败来源表并补测试，
   之后才考虑异常基类。**不做一刀切的 `ServiceError` 包装**——API 层依赖
   `ChangeExecutionError`、`TripPlanValidationError` 和超时的现有语义。

### CP8（可选）：构造函数依赖注入

`__init__` 注入 `settings / amap_service / poi_store`，默认值仍从
`get_settings()` / `get_*()` 取，测试用 fake 替换。改动面大，放最后。

## 5. 明确不做

- 不修改 `backend/app/models/schemas.py`，不改 ChangeSet JSON 结构
- 不拆 Create/Modify 双 Command（批评 #10 记录为远期，不动 API 契约）
- 不引入 `PlanningOrchestrator / FallbackPolicy / POIProvider` 等新目录或新类名——
  只有职责搬迁，不为理想架构先建空壳
- 不重写 `ChangeSetExecutor`
- 不合并 Amap REST / MCP / 图片服务
- 不删除确定性排程、ReAct、Validator 任一路径
- ReAct 历史保留每轮 Thought/Action/Observation 的约定不动

## 6. 风险提示

1. **`:236-248` 的"不降级"语义是全文件最贵的知识**：定向修改失败如实上报
   而非静默全量重排。重构中任何"补一个兜底重试"的手滑都会破坏产品行为。
   CP0 测试第 2 条就是防这个的。
2. `:507-517` 排程排序从"剩余集合最近邻"改为"经纬度地理投影"的注释记录了
   一次真实 bug 修复（南山片区跨组导致 Validator 失败）。搬
   `_build_evidence_plan` 时注释必须随行。
3. 本方案与 `2026-09-14-餐饮定向修改重构方案.md` 在定向修改流程上有交集，
   CP5 动工前必须先对账。
4. `docs/` 中目标架构名称（`IntentRecognizer`、`POIProvider` 等）按 0911
   方案 §1 约定仍不是当前代码事实，本文同样不把它们当作实施依据。

## 7. 验收标准

沿用 0911 方案 §8 并细化。每个 CP 完成时应能回答：

1. 完整规划从哪进入？行政区上下文在哪准备？（CP1/CP2 后）
2. Chroma 初始召回和 ReAct 工具搜索分别由谁负责？超时热身语义在哪？
   （CP3 后）
3. 确定性排程失败为什么回 ReAct？回退方向由谁保证？（CP4 后）
4. 定向 ChangeSet 失败后为什么如实上报而不是全量重排？（CP0/CP5 后）
5. `ChangeSetExecutor` 是否仍保证输入 `TripPlan` 不被原地修改？（CP5 后）
6. 最终 `TripPlan` 由哪个 Validator 交付？图片补齐为何在两种模式下跳过？
   （CP6 后）
7. 哪些异常由 Service 继续抛出，哪些由 API 层转 fallback？（CP7 后）
8. CP0 的 6 条特征测试在之后每个 CP 结束时全部通过？
